# かぎ針編み図アプリ 技術仕様書

このドキュメントは、実装の技術的な方針を定義する。編み物のルールは domain-spec.md、画面と操作は ui-spec.md、実装の順番は plan.md を参照する。

本書は方針レベルの決定を記録する。フォルダ構成の細部やクラス名などは、実装時に実際のプロジェクトに合わせて決め、決まったら本書に追記する。

---

## 1. 開発環境

- Mac と Xcode（最新の安定版）
- Git でバージョン管理する。1つのタスクが終わるたびにコミットする
  - リモートは GitHub。Jira のチケットごとにブランチを切り、PR を作る。マージは開発者が行う（運用の詳細は CLAUDE.md）
- 実装は Claude Code で行う。ビルドとテストがコマンドラインから実行できる状態を常に保つ
  - アプリのビルド：`xcodebuild`。署名なしで動くよう、コマンドラインではシミュレーター向けにビルドする（確認に使うシミュレーターは iPhone 17 と iPad Pro 11-inch）
  - アプリのテスト：`xcodebuild test`。共有スキームを用意し、UI テスト（AmizUITests）は通常のテストから外す（ターゲットは残す）
  - 編み図エンジンのテスト：`swift test`（4章の CrochetCore パッケージ内で実行）
  - 実際のコマンドは CLAUDE.md の「コマンド」に書く
- 開発者は iOS 開発がほぼ未経験（Rails / React の経験あり）

## 2. 対応OS・端末

| 項目 | 方針 |

| 最低対応OS | iOS 26.0 / iPadOS 26.0 以上（Xcode の初期値の 26.5 ではなく 26.0 に設定する。新しい API を使ったときに気づけるようにするため） |

## 4. 全体構成

アプリを「編み図エンジン」と「アプリ本体」に分ける。

| 部分 | 役割 | 置き場所 |
|---|---|---|
| 編み図エンジン | 編み図のデータ、目数や整合性の計算、図の座標計算 | ローカル Swift Package「CrochetCore」 |
| アプリ本体 | 保存、記号の描画、画面と操作 | Xcode のアプリターゲット |

### 4-1. 編み図エンジン（CrochetCore）

**置き場所と形**
- リポジトリ直下の `CrochetCore/` フォルダに置くローカル Swift Package（`Amiz/` フォルダの外。`Amiz/` は Xcode の同期フォルダで、中のファイルは自動でアプリターゲットに入るため）
- アプリターゲットからローカルパッケージの依存として参照する
- モジュールは `CrochetCore` の1つ。下の3層はフォルダ（`Model/`・`Compute/`・`Layout/`）で分け、必要になったらモジュール分割を検討する
- `platforms` には iOS 26 に加えて macOS 26 も書く（Mac 上で `swift test` を通すため。アプリは iOS 専用のまま）

中の構成は次の3層にする。

| 層 | 役割 | 例 |
|---|---|---|
| モデル | 編み図のデータ | 目の種類、操作、段、繰り返し、作り目、糸 |
| 計算 | データから導く値 | 手順の展開、目数（合計・鎖抜き）、整合性チェック、修正の影響範囲 |
| レイアウト | 図の座標 | 各目の位置・角度・高さ（円形図・平面図） |

**ルール**
- SwiftUI・UIKit・SwiftData を import しない
- Foundation（UUID、JSON 変換など）と CoreGraphics（CGPoint などの座標の型）は使ってよい
- 保存用のモデルとの変換は、6章の JSON 変換で行う
- テストは `swift test` で実行する（シミュレーター不要）

**モデル層の型**（`Sources/CrochetCore/Model/`。フェーズ1-1 で決定）

| 型 | 内容 | 対応する仕様 |
|---|---|---|
| `Pattern` | 編み図全体。`schemaVersion`、編み方、作り目、段の配列。`jsonData()` / `init(jsonData:)` で JSON と変換 | 5-4、6章 |
| `WorkingMethod` | 編み方：`flat`（往復編み）／`joinedRounds`（輪編み）／`spiral`（螺旋編み） | domain 5 |
| `FoundationKind` | 作り目：`magicRing`／`chain(stitchCount:)`。値は「1段目に編む目数」 | domain 33 |
| `Row` | 段。`id` と手順 `steps` | domain 21 |
| `Step` | 手順の1操作。`id` と `kind` | domain 21 |
| `StepKind` | 操作の種類：`turningChain`／`stitch`／`increase`／`decrease`／`skip`／`leaveRemaining`／`closeRound`／`repeatGroup` | domain 21 |
| `StitchKind` | 目の種類6つ。図での高さと立ち上がりの初期値を持つ | domain 1、6 |
| `Placement` | 編み入れ先：`stitch`（前段の目の頭）／`chainSpace`（束） | domain 3 |
| `RepeatCount` | 繰り返しの回数：`times(n)`／`untilEnd` | domain 15、17 |
| `StitchRef` | 展開後の1目を指す：段ID・操作ID・何回目・操作内の何目め | 5-3 |

- 「操作」は Foundation の `Operation` と、「作り目」は `Foundation` と名前が衝突するため、`Step`・`FoundationKind` にしている
- 画面のボタン1回＝1つの `Step` を原則にする（鎖編みを3回押せば `stitch(.chain)` が3つ並ぶ）。「n目編み入れる」「n目一度」と立ち上がりだけが数を持つ
- 「残りすべてに◯」は、単位が1つで回数が `untilEnd` の `repeatGroup` として表す
- `repeatGroup` の単位に `repeatGroup` を入れる（入れ子）ことは型の上では可能だが使わない。`count ≧ 2` などの条件も型では縛らず、計算層の検証で扱う

**計算層の型**（`Sources/CrochetCore/Compute/`。フェーズ1-2 で決定）

| 型 | 内容 | 対応する仕様 |
|---|---|---|
| `Expander` | 段の手順を展開する。`Pattern.expanded()` が省略形 | domain 15、17、21 |
| `ExpandedStitch` | 展開後の1目。どの操作から生まれたか（`StitchRef`）、種類、役割（普通／立ち上がり／段を閉じる引き抜き）、前段のどの目を拾ったか（`picks`）、数えるか | domain 6、7、8、21 |
| `RowExpansion` | 段の展開結果。目の列、拾った目数、前段の目数、「残りは編まない」の有無、繰り返しの実際の回数、問題（`issues`）。合計目数・鎖抜き目数は計算プロパティ | domain 8、17、23 |
| `PatternExpansion` | 編み図全体の展開結果（段ごとの `RowExpansion`） | |
| `ConsistencyChecker` | 段ごとの目数の警告を出す。`PatternExpansion.warnings(excludingRowAt:)` が省略形。入力中の段は呼び出し側が除外する | domain 23 |
| `RowWarning` | 警告。段の位置、種類（不足／過多）、警告文 | domain 23、ui 5-4 |
| `PatternEditor` | 段の編集（`RowEdit`：置き換え／削除／複製）の影響範囲を調べ（`EditImpact`）、「上の段を残す」「上の段をほどく」を適用する | domain 24、25、ui 7-1 |
| `StitchTableFormatter` | 目数表の文章（手順文・目数の表記）と、同じ内容の段をまとめた行（`StitchTableRow`）を作る。日本語の文字列はここに置く（多言語化は今後の拡張） | domain 8、18、19、ui 5-4 |
| `StitchModifier` | 先に選ぶボタンの状態（n目編み入れる／n目一度／束に／残りすべてに）。ボタンの切り替えルールと、目ボタンを押したときの `Step` への変換 | ui 5-6 |
| `PatternInput` | キーボードの操作を `Pattern` の変更に変換する純粋な関数（目を編む・立ち上がりの自動挿入・飛ばす・残りは編まない・1目削除・段を終える・繰り返しの終了・立ち上がりの手動設定）。入力中の段は `rows` の最後の段 | ui 5-6、domain 5、6、7、15、17 |

- 状態管理の分担：**状態遷移（reducer）は CrochetCore の `PatternInput`、状態の保持（store）はアプリの `EditorModel`**。編み物のルールに当たる判断はすべて `PatternInput` 側に置き、`swift test` で確かめる

**レイアウト層の型**（`Sources/CrochetCore/Layout/`。フェーズ3-1 で決定）

| 型 | 内容 | 対応する仕様 |
|---|---|---|
| `CircularLayout` | 円形図の座標計算。`Pattern.circularLayout()` が省略形。`Options` で単位の長さの設定（わの穴の半径、段の高さの下限、余白など） | 8-1 |
| `ChartLayout` | 図全体の結果。目ごとの `LaidOutStitch`、段ごとの `RowRing`（内外の半径）、外接矩形。`StitchRef` からの検索、（段, 数える目の位置）からの検索（ハイライト用）、一番近い目の検索（タップ判定） | 7 |
| `LaidOutStitch` | 図に置かれた1目。頭の座標、根元の座標の配列（鎖は0個、普通は1個、n目一度は n 個）、記号の向きと長さ、極座標 | domain 11、12 |

- 座標の単位は「鎖1目分」＝1.0。描画側で倍率をかける。画面座標（右が +x、下が +y）で持つ

- 影響範囲の判定：置き換えは目数が変わったときだけ、削除・複製は上に段があれば必ず確認する。影響を受けるのは編集した段より上のすべての段
- 段の複製は `Row.duplicated()` で段と操作の ID をすべて新しくする。手順の比較は ID を無視する `Row.hasSameSteps(as:)` で行う

- 立ち上がりは鎖の目数に関わらず展開後は1要素（数えるときは1目）。図では鎖の数だけ描く
- 「前段の目数」は前段の合計目数（鎖を含む）。段の展開結果から次の段へ渡す

**JSON の形**：操作は `type` で種類を見分ける平らな形にする。自動生成に任せず自分で変換を書く（自動生成だと `_0` のようなキーになり、型名の変更で古いデータが読めなくなるため）。`type` や列挙の文字列は保存形式の一部なので変更しない。

```json
{
  "schemaVersion": 1,
  "method": "joinedRounds",
  "foundation": { "type": "magicRing" },
  "rows": [
    { "id": "…", "steps": [
      { "id": "…", "type": "turningChain", "chains": 1 },
      { "id": "…", "type": "repeat", "count": 6, "unit": [
        { "id": "…", "type": "stitch",   "stitch": "singleCrochet", "into": "stitch" },
        { "id": "…", "type": "increase", "stitch": "singleCrochet", "count": 2, "into": "stitch" }
      ]},
      { "id": "…", "type": "closeRound" }
    ]}
  ]
}
```

その他の操作：`{"type":"decrease","stitch":"singleCrochet","count":2}`、`{"type":"skip"}`、`{"type":"leaveRemaining"}`。段の終わりまでの繰り返しは `"count": "untilEnd"`。鎖の作り目は `{"type":"chain","stitchCount":20}`。

**SwiftData を import しない理由**
- 目の順番を確実に扱うため。SwiftData の関連データの配列は、保存・読み込みで順番が保証されない。段の中の目の順番がすべてのこのアプリでは、並び順の管理があらゆる処理に入り込んでしまう
- 元に戻す（9章）を、値型のデータのコピーで実現するため。`@Model` はクラス（参照型）にしか付けられない
- iCloud 同期のためのモデルの制約（全プロパティに初期値を持たせる、など）を、編み図のルールの書き方に持ち込まないため
- テストのたびにデータベースの準備をしなくて済むようにするため

**SwiftUI・UIKit を import しない理由**
- 目数計算や整合性チェックなどの計算ロジックが、画面のコードに混ざるのを防ぐため
- import の有無で、エンジンと画面の境界を機械的に確認できるようにするため
- ドメイン仕様のルールは、原則すべてこのパッケージに実装する

### 4-2. アプリ本体

- 保存（SwiftData）
- 記号の描画（Canvas）。エンジンのレイアウト結果を受け取って描くだけにし、座標計算はしない
- 画面と操作（SwiftUI）

**編集画面の状態管理**（`Amiz/Editor/EditorModel.swift`。フェーズ2-1 で決定）
- `@Observable` の `EditorModel` が、今の `Pattern`、展開結果（変更のたびに計算し直す）、先に選ぶボタンの状態、繰り返し開始の位置、元に戻す／やり直しの履歴を持つ。React の store に当たる
- 画面のボタンは `press…` を呼ぶだけで、編み図の変更は `PatternInput` に委ねる
- 元に戻す／やり直しは、変更のたびに `Pattern` 全体のコピーを履歴に積む（9章）。戻したときは先に選ぶ状態と繰り返し開始の位置を解除する

## 5. データ設計の方針

### 5-1. 保存するのは「ユーザーの入力」だけ

- 保存するもの：作り目、各段の手順（操作の列・繰り返しの構造）、糸リスト、目ごとの色
- 保存しないもの：展開後の目の列、目数、警告、図の座標
- 保存しないものは、表示のたびにエンジンで計算する。保存データと計算結果が食い違う不具合を防ぐため

### 5-2. 値型で表現する

- 編み図のデータは `struct` と `enum` で表現する（React の state をイミュータブルに扱う考え方に近い）
- `Codable`（JSON に変換できる）と `Sendable`（並行処理で安全に扱える）に準拠させる

### 5-3. IDを持たせる

- 段・操作・繰り返しには、それぞれ一意のID（UUID）を持たせる
- 目の選択、修正の影響範囲の計算、元に戻す操作で、対象を確実に特定するため
- 繰り返しは展開せずに保存するため、繰り返しの中の個々の目（「3回目の2目め」など）には ID がない。展開後の目は「（段ID, 操作ID, 何回目）」の組で指す方針とし、具体的な形はデータモデル設計のタスクで決める

### 5-5. アプリの設定

- 設定画面の項目（ui-spec 6-3。立ち上がりの自動入力、段番号の表示）は作品に依存しないアプリ全体の設定なので、UserDefaults（SwiftUI では `@AppStorage`）に保存する。編み図データには含めない

### 5-4. データのバージョン

- 編み図データに `schemaVersion` を持たせる
- 将来データ構造を変えたとき（玉編みの追加など）に、古いデータを読み込めるようにするため

## 6. 保存

- SwiftData のモデルは「作品（Work）」1つを基本にする
  - 作品名、編み方、作成日、更新日、サムネイル画像
  - 編み図本体（5章のデータを JSON にした `Data`）
- 編み図本体を細かいテーブルに分けず、1つの JSON として保存する
  - 理由：編み図は段・操作・繰り返しが入れ子になった構造で、細かいテーブルに分けると保存処理が複雑になる。エンジンを SwiftData から独立させる（4-1）ためでもある
- 編集内容は自動保存する（保存ボタンは設けない）
- iCloud 同期は将来対応とする。ただし後から同期を有効にできるよう、SwiftData のモデルは CloudKit の制約に沿って定義する（すべてのプロパティに初期値を持たせる、一意制約を使わない、など）

## 7. 記号図の描画

- SwiftUI の Canvas で、1つの図をまとめて描く（目ごとに View を作らない。数百〜数千目でも重くならないようにするため）
- 記号は画像素材を使わず、Path で線として描く（ドメイン仕様10）
- 描画の流れ：エンジンのレイアウト結果（目ごとの位置・角度・高さ・色）を受け取る → Canvas で描く
- ズーム・移動は、描画全体に拡大・移動の変換をかけて実現する
- タップした目の判定は、レイアウト結果の座標から一番近い目を探して行う
- 描画のパフォーマンス最適化（表示範囲外を描かない、など）は、大きな図で試して必要になってから行う

## 8. レイアウト計算の方針

詳細なアルゴリズムは実装時に試作して決める。基本の考え方は次のとおり。

### 8-1. 円形図（輪編み・螺旋編み）

- 段ごとの半径：作り目からの段の高さ（鎖○目分）の累計で決める
- 目の角度：編み入れ先の目の角度を基準にする
  - 同じ目に複数編み入れた場合：基準の角度の周りに均等に広げる
  - 2目一度：拾った目の角度の中間にする
  - 鎖編み（前段に編み入れない）：前後の目の角度の間に等間隔に並べる
- 最後に、段全体で記号が重ならないよう角度を調整する
- 記号の向き：根元が編み入れ先の方向を向くように回転させる（ドメイン仕様12）

**具体化（フェーズ3-1）**：上の4点を、次の1つの手順で実現する。
- 段の内側の半径＝前の段の外側の半径、外側の半径＝内側＋その段で一番高い目の高さ（下限1）。わの作り目の穴の半径は 0.8
- **数える目の「頭」を段の円周に等間隔に並べ、「根元」は拾った前段の目の頭の角度に置く**。これで、増し目は根元を共有して頭が広がり（V字）、減らし目は根元が複数で頭が1つ（逆V字）、増減なしの段は放射状になり、記号どうしは重ならない
- 頭の並び全体の回転量は「頭と根元の角度差の平均が 0」になるように決める（V字が左右対称になる）
- 鎖編みは根元なしで頭の位置に接線方向で置く。数えない立ち上がり（鎖1目）は段の始めの半歩手前、段を閉じる引き抜きは段の終わりの半歩後ろ
- 角度は3時の位置が 0 で、画面上で反時計回りに進む
- この方針で実物に近い見た目になるかはフェーズ3-4 で判断する（13章）

### 8-2. 平面図（往復編み）

- 目の横位置：編み入れ先の目の横位置を基準にする（考え方は円形図と同じ）
- 段の縦位置：段の高さの累計
- 図の座標は編み地の表から見た向きで固定し、段ごとに「手順を進める方向」が反転する

## 9. 元に戻す・やり直し

- 編集操作のたびに、編み図データ全体のコピー（スナップショット）を履歴に積む
  - 値型なのでコピーが簡単で、差分を管理する方式より不具合が起きにくい
- 操作の単位
  - キーボードのボタン1回＝1単位
  - 過去の段の編集は「完了」までを1単位
  - 色編集モードでなぞって塗った1回＝1単位
- 履歴は作品を開いている間のみ保持する（アプリを閉じたら消えてよい）

## 10. 書き出し

- ImageRenderer で、描画用の View を PDF（A4）と画像に変換する
  - ImageRenderer は1回の描画で1ページを作る。目数表が長く A4 に収まらない場合の複数ページへの分割は自前で行う必要があり、書き出しの実装時に扱う
- ShareLink で iOS 標準の共有シートを開く
- 図・目数表・凡例・糸リストは、書き出し用のレイアウトを画面表示とは別に用意する

## 11. テスト方針

- **編み図エンジン**：Swift Testing で単体テストを書く
  - domain-spec.md のテストケース（TC-1〜）は、必ず自動テストにする
  - 新しいルールを実装するときは、テストを先に書く
- **アプリ本体**：SwiftUI のプレビューとシミュレーターでの手動確認を中心にする。UI の自動テストは最小限にする
  - UI テストターゲット（AmizUITests）は通常のテスト実行（共有スキーム `Amiz`）からは外し、別の共有スキーム `AmizUITests` で必要なときだけ走らせる。起動時間が長く、毎回のタスクで走らせる価値が薄いため
  - UI テストは「ボタンを押すとモデルが動き、画面に反映される」ことを確かめる最小のもの（1〜2本）にとどめる。ボタンには `accessibilityIdentifier`（`stitch.singleCrochet`、`op.finishRow` など）を付けて指す
- 1つのタスクの完了条件は「ビルドが通り、すべてのテストが通ること」

## 12. コードの書き方

- 型や変数の名前は英語。編み物の用語は domain-spec.md の用語表（US式）に合わせる
- コメントは日本語でよい
- 1つのファイルには1つの役割だけを持たせる
- 開発者が理解しながら進められるよう、変更のたびに何をしたかを説明する。SwiftUI の概念は React との対比で説明すると伝わりやすい
